# WFM SQL Dashboard

A workforce-management dashboard for a **fictional** contact center, where every number comes from a plain SQL query and the query is shown next to each chart.

**Live demo: [wfm-sql-dashboard.vercel.app](https://wfm-sql-dashboard.vercel.app)**

![The dashboard: service level, KPI tiles, forecast vs actual chart, service-level heatmap and staffing-gap chart](docs/images/dashboard-desktop.png)

## In 60 seconds

- **What it is:** 3 queues, 8 weeks of 30-minute data, and 8 SQL questions a WFM analyst asks every week (service level, abandons, forecast accuracy, staffing gap, adherence). A web page draws the answers, with filters and a "Show the SQL" panel under every chart.
- **Who made it:** a Workforce Management Analyst learning SQL. I know the WFM side well; I'm a beginner at SQL and programming. **Claude Code (an AI assistant) wrote most of the code**, see [below](#what-i-did-and-what-the-ai-did).
- **The data is synthetic.** It is generated by a script with a fixed random seed. No real employer, customer or employee data was used, and the agent IDs (`AGT-001`) are made up. The results show how the queries work, not how a real contact center performs.

## Tech used

| Layer | What |
|---|---|
| Database and queries | SQLite (one file, [`data/wfm.db`](data/)); plain `.sql` files using `GROUP BY`, `CASE`, `NULLIF`, `WITH` steps, the `LAG` window function, `JOIN` and `UNION ALL` |
| Scripts | Python 3 standard library only: data generator, query runner, dashboard export, and a checker that re-calculates every query result independently (14 checks) |
| Dashboard | Plain HTML, CSS and JavaScript, plus Chart.js 4.4.7 for two charts; no framework and no build step |
| Hosting | Vercel (static site), deployed automatically from this GitHub repo |

## The 8 questions it answers

Each query is a file in [`sql/`](sql/) and is explained line by line in [docs/LEARNING.md](docs/LEARNING.md).

| # | Question | File |
|---|---|---|
| 1 | How many contacts did each queue get each day? | [`01_offered_per_day_queue`](sql/01_offered_per_day_queue.sql) |
| 2 | What is each queue's average handle time (weighted by contacts)? | [`02_aht_per_queue`](sql/02_aht_per_queue.sql) |
| 3 | What service level did each half-hour get, against the 80/20 target? | [`03_service_level_per_interval`](sql/03_service_level_per_interval.sql) |
| 4 | What share of contacts hang up, per queue per week? | [`04_abandon_rate_weekly`](sql/04_abandon_rate_weekly.sql) |
| 5 | How accurate was the forecast (MAPE, WAPE and bias)? | [`05_forecast_accuracy`](sql/05_forecast_accuracy.sql) |
| 6 | How did weekly volume change week over week? | [`06_wow_volume_change`](sql/06_wow_volume_change.sql) |
| 7 | In each half-hour, how many agents were needed vs scheduled? | [`07_staffing_gap`](sql/07_staffing_gap.sql) |
| 8 | How well did each team and each agent keep to their schedule? | [`08_adherence_team_agent`](sql/08_adherence_team_agent.sql) |

## Run it yourself

Needs Python 3 and nothing else.

```bash
python scripts/run_sql.py                                  # list the queries
python scripts/run_sql.py sql/03_service_level_per_interval.sql --limit 20
python scripts/verify_queries.py                           # re-check every result with plain Python
python scripts/export_dashboard.py                         # regenerate the dashboard data
python -m http.server 8000 --directory dashboard           # then open http://localhost:8000
```

## Limits, stated plainly

- Synthetic data: plausible, but not proof that anything works on real data. Service level comes from a smooth curve of agent load, not a queue simulation. Details in [docs/DATA.md](docs/DATA.md).
- The staffing gap uses a simple formula (workload ÷ 85% occupancy), not Erlang C, and the data generator used the same idea, so the two agree by design. Erlang C is the natural next step.
- No wait times in the data, so very short abandons can't be excluded. Light theme only; touch use on phones was not tested.
